The problem

Three suspects.
No witness.

Rina routes a mid-cap through the pool her wallet picked and is filled under the quote. She spends the evening convinced a bot ate her.

Every tool shows her volume and 24 h transactions — exactly the two numbers a wallet trading with itself inflates. So she picks the busiest pool and sets a loose cap "to be safe".

A trader sees two numbers before a swap and one after, and the gap has three possible authors. Nothing on any aggregator says which — and the number she uses to choose the pool is the one a wash wallet inflates most.
The solution

One table names it.

The last {{prints}} real prints of a token from CoinMarketCap's keyless feed, ordered by block and log index, joined on the maker address. One row per pool. One line under it.

round-tripthe same wallet's next print in the block is the other side, size within 5 % — removed and counted

routethe pool with the lowest organic p90; that p90, rounded up, is the cap

RETRACTED · 2026-09-18

This project was decided as the sandwich rate per pool. The day-1 spike found zero same-block sandwiches in 1,200 prints; the census found two in {{census.prints}}. So the headline changed before the build, not the caveat after — same feed, same ordering, same join; the sandwich is one named case of a middleman, and the number the page leads with is the one the join actually found. On 2026-09-20 the same command found 17 sandwiches in one window on a different pair — small on average is not small everywhere.

We were going to sell you a sandwich detector. We measured, and the rate was two in eight thousand. The engine did not change — the same join finds both shapes — but the headline did, before the build, and the README carries that retraction with a date. What the join did find is a wash pattern big enough to put a pair at the top of the sponsor's own ranking.

What this is not · the full list of six is on the README

Where it stops.

The window is {{prints}} prints, not 24 h

{{hero.span}} h on the hero, 20 h on SHIB. The span is on every row; the receipt carries the window's share of the pool's 24 h count — {{hero.coverage_1}} here.

Uniswap v3 fee tiers of one pair merge

The feed carries no pool address. A row marked ×n is n pools sharing (venue, base, quote) — marked, never guessed. Filed as FEEDBACK.md §6.

Quote-to-fill is a realised, fee-inclusive move

Consecutive opposite-side prints straddle the fee twice, so p90 sits near 60 bps on every busy 0.30 % pool. It is used comparatively, across pools of one token in one window.

A round-trip is a shape, not a verdict

Same wallet, same block, opposite sides, size-matched. The rows and the definition are printed; nobody is labelled a bot. The anonymous tier throttles per IP — the tool backs off and exits 75 if the quota is spent.

Four things it does not claim. The window is eight hundred prints, not a day. Fee tiers merge because the feed has no pool address. The cost number is fee-inclusive and only meaningful across pools of one token. And a round-trip is a shape — we print the rows and the rule, never a label on a person.
